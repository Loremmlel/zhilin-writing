# 知临中学 Playwright 行为测试评估

日期：2026-09-06  
分支：`feat/playwright-behavior-tests`  
状态：暂缓，不实施

## 决策

当前不在知临中学仓库引入 Playwright，也不把浏览器测试列为发布门槛。

原因不是测试目标不成立，而是项目的主要开发环境是 ChatGPT Work 沙盒；测试必须先在这里真正执行，才值得进入仓库。此前先写完 18 条测试、再等待其他环境验收的顺序是错误的，相关实现已撤回。

## 已验证的环境事实

- Sites 本地预览可以启动，应用与本地 Cloudflare 运行时本身可用。
- 沙盒没有 Chromium、Chrome、Firefox 或 Playwright 浏览器缓存。
- 当前网络策略无法完成 Playwright Chromium 下载。
- Work 自带的受控浏览器不是仓库内 `@playwright/test` 可调用的浏览器进程；本次还无法访问 Sites 本地预览。

因此，仓库内的 Playwright 命令无法在主要开发环境形成“启动应用、操作浏览器、断言结果、清理 D1/R2”的闭环。

## 当前测试策略

继续使用已经能在沙盒稳定执行的检查：

- `node:test` 验证领域行为、权限、迁移、事务、DOCX、批注算法、IndexedDB 和 Worker 合同。
- `npm test` 验证完整单测、生产构建和少量最终产物合同。
- 测试仍按稳定产品能力维护，不因每个 Bug 新建独立回归文件；优先补强已有功能合同。
- 真实点击、焦点、拖拽选区、响应式交互等浏览器行为，在可用浏览器基础设施出现前明确记为未自动验证，不用源码字符串断言冒充浏览器验证。

## 不采用的替代方案

- 不让写入型测试连接正式 D1/R2。
- 不增加生产可访问的测试种子接口或鉴权后门。
- 不自制一套模拟浏览器或把 Happy DOM 称为端到端测试。
- 不依赖只能由当前对话工具手动驱动、无法由仓库命令复现的内部浏览器脚本。

这些方案要么有数据风险，要么制造假的测试信心。

## 重新引入 Playwright 的门槛

只有同时满足以下条件才重新实施：

1. 当前主要开发环境能提供 Playwright 可调用的浏览器二进制或正式支持的远程连接。
2. 浏览器能访问当前 checkout 的本地 Sites 预览。
3. 一条最小写入旅程可以使用一次性本地 D1/R2 完整运行并清理。
4. 上述证明可以由仓库中的单条命令重复执行，不依赖人工工具操作。

达到门槛后，先只做一条代表性发布旅程。它稳定通过两轮后，再按产品能力逐步增加，而不是一次写完 18 条未运行的测试。

此前的完整场景草案仍保存在 Git 历史提交 `c49b8bb` 中，只作为未来参考，不代表当前承诺。
