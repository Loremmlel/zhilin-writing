# 浩劫 2 接入知临中学：HTTP＋轮询实施方案

日期：2026-09-20。状态：已按本方案完成实现；自动化验证与浏览器验收限制见 [实施验证记录](../testing/haojie-online-verification.md)。下文保留设计依据和验收目标，不代表所有真实浏览器场景已经通过。

## 1. 技术选择与改动归属

采用 **现有 Sites 网站＋HTTP 接口＋短轮询＋现有 D1 数据库**。浏览器提交操作，网站服务端调用浩劫规则引擎结算并持久化；另一名玩家通过轮询取得自己的最新视图。每个请求独立处理，对局不依赖某个 Worker 实例持续运行。

| 部分        | 负责内容                                              | 本轮安排                                           |
| ----------- | ----------------------------------------------------- | -------------------------------------------------- |
| 浩劫 2 仓库 | 游戏规则、命令校验、玩家视图、受控棋盘与动画          | 复用已验收代码；集成若发现通用问题，再回原仓库修复 |
| 网站仓库    | 登录和席位、房间、HTTP API、D1 持久化、轮询、断线恢复 | 本轮主要开发位置                                   |
| Sites       | 托管网页与请求处理、提供既有 D1 绑定                  | 沿用现有部署配置                                   |

首版不需要新增 WebSocket、SSE、Durable Objects、Redis 或 Linux 虚拟机。已有独立探针确认普通 WS 能连接，但当前 Sites 标准部署流程未提供可用的 DO 绑定；所选方案不依赖这些能力。

代码基线：网站 `e1bc28013580dd70b7b92dab8967c12e0e9e3920`；浩劫 2 [PR #8](https://github.com/Loremmlel/haojie2/pull/8) 合并提交 `7824f47c0deb0797819833f6641021f87f4aecbd`。实施前再核对主线变化。

## 2. 首版用户流程

1. 在网站账户菜单增加“浩劫 2”，进入 `/games/haojie`。沿用现有登录、白名单和站内资料要求。
2. 首页显示“创建房间”和“我的未结束对局”。创建时选择经典／神龛模式，默认经典。
3. 创建者占 1 号位，获得随机房间链接。邀请链接打开后，符合网站访问权限的另一名用户点击“加入对局”，占 2 号位并开始游戏。
4. 房间页 `/games/haojie/[roomId]` 显示双方昵称、模式、等待／对局／结束状态和棋盘。使用原有 `HaojieOnlineGame`，保留规则、图鉴、音效和游戏内交互。
5. 关闭页面或刷新后，原账号回到原席位，恢复最新局面。离开页面不算认输；暂不设置掉线判负和回合时限。
6. 等人时创建者可取消；开始后任一玩家可确认认输。自然胜负由引擎判定。结束后可查看最终局面，下一局创建新房间。

同一账号不能占两个席位；第三人不能加入已满房间或读取棋局。持链接的合格成员可加入空位，未加入前只返回必要的房间介绍，不返回棋局。自己的多个标签页可打开同一局，写入冲突由服务端处理。

首版不包含公开房间大厅、随机匹配、观战、排行榜、聊天、联网悔棋和历史逐步回放。房间生命周期为 `waiting → playing → finished`，或 `waiting → cancelled`；结束的房间不复用为新对局。

## 3. 源码接入方式

- 将固定提交的浩劫源码及所需静态资源同步到网站 `vendor/haojie2/`，记录来源、完整 SHA 和同步方法；保留原文件结构及原有版权信息。无需先发布 npm 包，也不在部署时拉取浮动的 `main`。
- 服务端从 `src/engine/index.ts` 导入 `createGame`、`applyPlayerCommand`、`getPlayerView`、`canRebasePlayerCommand` 等接口。
- 客户端直接导入 `src/ui/online/HaojieOnlineGame.tsx`，按路由加载，复用网站已有 React；普通写作页面不加载游戏资源。
- 网站只写宿主适配层，不复制棋盘或另写技能规则。游戏界面沿用 `.hj-game` 作用域样式；外围导航、按钮、确认框、错误和布局复用网站规范。
- 前后端使用同一份固定游戏代码；房间记录引擎 SHA、`HAOJIE_RULESET` 和 `PLAYER_VIEW_VERSION`。浏览器提交时携带版本标识，版本不匹配先阻止操作并提示刷新。
- 活动对局不能静默换规则。首版升级游戏规则前先结束旧版本活动对局；普通网站部署只要保持该游戏版本，就可继续原对局。暂不增加多引擎版本并行运行机制。

## 4. D1 数据模型

在现有数据库新增两张独立业务表，不更改帖子、批注或用户数据结构。

| 表                | 主要字段／约束                                                                                                          | 用途                                         |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `haojie_rooms`    | 随机 ID、双方用户 ID、模式、状态、`revision`、完整 `state_json`、引擎版本、最后变化类型、结束原因／胜者、创建／更新时间 | 保存唯一权威局面和房间元数据                 |
| `haojie_requests` | 房间 ID、操作者 ID、`request_id`、操作类型、规范化请求摘要、成功修订号、时间；`(room_id, actor_id, request_id)` 唯一    | 为加入、游戏命令、取消／认输提供成功回执去重 |

补充约束与索引：

- 建房以 `(创建者, 创建请求编号)` 唯一，网络重试返回同一个房间；相同编号配不同模式应拒绝。
- 两个席位不能属于同一用户。房间查询按主键；“我的对局”按参与者、状态、更新时间建索引，并复用网站分页。
- 请求记录引用房间。游戏开始时服务端用 `crypto.getRandomValues` 生成种子，再调用 `createGame(seed, mode)`；完整状态中的种子和 RNG 只留在服务端。
- 等待房间可无棋局；第二位玩家加入时，把席位、初始状态、状态变更与回执一同原子保存。
- `revision` 是房间修订号。加入、有效游戏命令和结束都递增，不能拿游戏回合数或存档版本替代；重复请求不递增。
- 认输由房间层记录胜者与结束原因，锁定棋盘，不伪造一条游戏技能命令或改写游戏规则。
- 暂不自动清理房间及去重记录；后续清理应按整局处理。不能在仍允许请求重试时提前删除成功回执。

只保存当前权威状态和轻量成功回执；不为每一步额外保存完整快照。刷新续局不需要服务器常驻内存。

## 5. HTTP 接口

| 接口                                        | 行为                                                                                                 |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `GET /api/haojie/rooms`                     | 分页返回本人房间摘要                                                                                 |
| `POST /api/haojie/rooms`                    | 使用创建请求编号创建房间，返回邀请地址                                                               |
| `GET /api/haojie/rooms/[id]?after=revision` | 返回房间元数据及本人玩家视图；无变化返回 `204`；首次请求省略 `after`                                 |
| `POST /api/haojie/rooms/[id]/join`          | 原子占用第二席并开始；本人重复加入返回原席位                                                         |
| `POST /api/haojie/rooms/[id]/commands`      | 接收 `{requestId, baseRevision, engineVersion, command}`，校验、结算、持久化后返回成功回执和本人视图 |
| `POST /api/haojie/rooms/[id]/finish`        | 携带请求编号和基础修订号，执行取消或认输；按状态和本人权限校验                                       |

接口复用 `getApiMemberAccess()`；每次请求重新验证登录、白名单和房间权限，席位由服务端账号映射。管理员身份本身不授予查看他人隐藏局面或替他人操作的权限。

所有响应设置 `Cache-Control: private, no-store`。写入只接受同源 JSON，并验证来源和实际请求体大小；首版请求体上限定为 16 KiB，解析后继续执行游戏命令校验。限制异常提交频率和自动重试次数。

成功响应中的回执修订号必须对应已经提交的事务；返回的视图可以更新，但不能比该回执旧。非法命令不推进状态；过期操作返回 `409` 及授权玩家的最新视图；认证失效返回 `401/403`。未预期的服务端错误沿用 `logServerError` 和 `incidentId`，不暴露完整状态、请求体、种子或内部异常。

## 6. 并发与幂等：必须一起提交

一次游戏命令的服务端流程：

1. 验证当前账号与席位，解析请求。先查该账号在本房间的成功回执：相同请求编号、相同内容直接返回原成功结果；相同编号、不同内容拒绝。
2. 读取最新权威状态及修订号，检查房间状态和引擎版本。通常必须匹配客户端 `baseRevision`。
3. 唯一的过期重算例外由 `canRebasePlayerCommand` 判断：允许仍有效的双方首次独立神龛暗选。网站不自行识别技能，也不自动重放过期攻击或移动。
4. 调用 `applyPlayerCommand(state, authenticatedSeat, command)` 计算候选新局面。这一步尚未保存，也不能回成功。
5. 在同一个 D1 `batch` 事务内，完成修订号／房间状态保护、插入唯一成功回执、写入新局面和新修订号。
6. 事务提交后，通过 `getPlayerView` 返回该玩家视图。若竞争失败，重新检查成功回执及最新状态：已成功的同一请求返回成功；普通过期请求返回冲突；仅引擎认可的独立暗选允许有限次重新结算。

实现沿用网站已有的事务保护思路：保护语句在条件不满足时触发数据库约束失败，使整个 batch 回滚。特别注意，**普通 `UPDATE ... WHERE revision = ?` 更新 0 行不会自动令 batch 失败**；不能让后续“成功回执”仍被插入。房间不存在也必须由外键等约束保证无法写入孤立成功回执。

D1 官方说明 `batch` 内语句按顺序执行，失败会使整批回滚；实现应以真实 D1 绑定验证该行为。[Cloudflare D1 Database 文档](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)

首版沿用网站当前普通 D1 绑定访问方式，不主动启用读副本。官方文档说明，不使用 Sessions API 时查询仍走主库，因此当前方案无需增加跨请求书签协议。[Cloudflare D1 Sessions 说明](https://developers.cloudflare.com/d1/worker-api/d1-database/#withsession)

该设计的目标是：同一步重试只执行一次；不同操作竞争时不会相互覆盖；实例更换后仍从数据库恢复。它不要求数据库事务跨越 JavaScript 引擎计算。

## 7. 轮询与断线恢复

- 房间页可见时，上一轮 GET 结束后约 1 秒发起下一轮，始终只有一个轮询请求在途。页面隐藏后改为约 10 秒；回到前台或网络恢复时立即同步。房间结束后停止轮询。
- 无变化返回 `204`。数据库查询按房间主键读取权限和修订信息，仅在有变化时返回完整状态字段；无变化不传输／解析整份游戏状态，也不写房间心跳。
- 有效落子由 POST 响应立即更新本人棋盘，不必等待下一轮 GET。对手的可见延迟约为轮询等待加请求耗时，需以实际网络验收，不能承诺固定一秒以内。
- 自己的回合仍继续轮询；反应和回合外技能交由游戏组件判断，不能以“不是你的回合”为由统一禁用组件。
- 更新先按房间 ID 和修订号过滤，旧响应不覆盖新局面。首次进入、重连、跨过多个修订、加入／结束等非游戏命令变化使用 `kind: 'snapshot'`；仅连续的一步游戏变化使用 `kind: 'update'`，避免遗漏或重复动画。
- 游戏组件需同时取得“本次成功回执”和“不早于成功修订号的局面”才解锁；任意一次轮询更新不能代替本次回执。
- POST 超时、连接中断或不确定的 `5xx`，先标记正在重连并锁定新操作；恢复后用**原请求编号、原请求内容**重试，服务端先查回执。取消浏览器请求不代表服务端回滚，不能立刻生成新编号重做同一步。
- 重试采用有上限的退避，例如 1、2、4、8 秒并加少量随机延迟；多次失败保留局面和“重新连接”入口。重新加载页面则重新获取权威快照，不自动重放旧页面操作。
- 明确的规则拒绝或版本冲突提示原因、同步后允许重新选择；认证失效停止轮询并进入已有登录／无权限恢复流程。

界面显示本机的同步／重连状态，不用“最后轮询时间”冒充对手在线状态。

## 8. 请求成本与现有网站适配

按两名玩家各约每秒一轮估算，一局活跃对局约 2 次轮询请求／秒，即约 120 次／分钟；每次还包含认证和房间读取。这是请求量估算，不是价格或容量承诺。后台降频、非重叠轮询和结束停轮询会降低实际数量。

现有 `worker/index.ts` 会在响应就绪及有响应体的流结束时写性能记录。需要为游戏轮询增加采样策略：正常轮询少量采样，例如 1%；命令和异常保持完整诊断，保留响应中的请求编号及耗时。采样应覆盖同一请求的两个日志阶段，不能只跳过其中一处。继续复用 `measuredDatabase`，不记录命令内容与私有状态。

验收时观察请求耗时、D1 读写次数和日志增长。若用户规模或数据库负载扩大，可先把轮询调到 1.5～2 秒；当前不因未来可能增长而引入新服务。

## 10. 实施顺序、验收与发布

**第一步：打通持久化后端。** 增加迁移和房间接口，接入纯引擎，用实际 D1 测试绑定验证抢座、并发保护、回执去重和回滚，再做前端。

**第二步：接入房间和棋盘。** 完成邀请、轮询、恢复和结束流程，检查网站实际构建、按路由加载、样式作用域及窄屏布局。

**第三步：双账号验收。** 使用隔离测试数据与独立数据库，不把测试迁移指向现有生产 D1。实际运行并记录以下结果：

| 场景                         | 通过标准                                                                       |
| ---------------------------- | ------------------------------------------------------------------------------ |
| 两账号加入并完整对局         | 经典／神龛可运行，双方自己的视图与胜负一致                                     |
| 同时抢占第二席               | 只有一个账号成功；第三人无法读写棋局                                           |
| 双方同时暗选                 | 两次有效独立选择均可接受，共同揭示前不泄漏另一方选择                           |
| 同一步重复发送、保存后丢响应 | 仅执行一次，原编号重试拿到原成功修订号                                         |
| 同基础版本的不同操作竞争     | 普通操作最多一个成功，无覆盖、无孤立成功回执                                   |
| 中途注入持久化失败           | 局面、修订号和成功回执一起回滚                                                 |
| 刷新、短暂断网、前后台切换   | 恢复权威局面，不重复执行，不重复动画，轮询不叠加                               |
| 跳修订与 POST／GET 乱序      | 只显示最新状态；本次操作只由自己的回执确认                                     |
| 回合外技能与对手反应         | 自己回合也能收到更新；应有操作不被宿主误锁                                     |
| 权限与私有信息               | 撤销白名单后停止访问；响应不含 seed、rng 或隐藏选择                            |
| 游戏版本不一致               | 拒绝提交并给恢复提示；不静默切换活动对局规则                                   |
| 网站与负载回归               | 登录、文章阅读／保存可用；普通页面不加载游戏；空轮询不持续写房间或全量性能日志 |

最后做真实 Sites 环境双客户端验证，区分本地测试、隔离部署测试和真实浏览器证据；模拟宿主测试不能代替这一步。

发布沿用原站点项目和 D1／R2 绑定，只执行新增游戏表的迁移。准备一个同时约束游戏页面和 API 的入口开关；通过验收后再发布并开放入口。若出现问题，关闭游戏入口和写入，或回到兼容的先前网站版本；新增表与已保存对局保留，不做删表回滚。上线前记录原部署版本和恢复步骤。

交付物应包括：网站集成改动、迁移、固定游戏源码来源、关键验证结果及发布／回退记录。浩劫仓库现有受控接口是接入基础，是否需要补充调整以实际网站构建和联机验收结果为准。
